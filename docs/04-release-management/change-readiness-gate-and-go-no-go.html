Change Readiness Gate & Go/No-Go Meeting

Skill: Release governance · Standard: ITIL 4 Change Enablement (CAB / change authority)

Without explicit criteria, readiness reviews turn into status meetings, and decisions go to whoever sounds most confident. A gate makes readiness a checkable state that's evaluated before the meeting, so the meeting only has to deal with exceptions.

Part 1: The gate

An item is Ready only when all mandatory criteria pass. Advisory signals add context but never block on their own.

Mandatory criteria (examples; tailor them to your process)

#CriterionEvidence sourcePass rule
M1Planned date falls in the review windowPlanned release dateWithin the configured window
M2Work is complete and verifiedTracker statusStatus is in your organisation's "verified" set
M3Test evidence existsLinked test runA passing regression run since the last code change
M4Rollback plan existsLinked documentReviewed by the owning team
M5No blocking defectsLinked defectsZero open defects at the highest severity

Advisory signals

#SignalWhy it matters
A1Stakeholder acceptance completedReduces acceptance surprises
A2Release owner assignedSomeone is accountable
A3Change is unplanned / expeditedGets closer scrutiny

Outcome states

StateMeaningAction
✅ ReadyAll mandatory criteria passConsent agenda: approve without discussion
🟡 At riskA gap that can be fixed before the reviewNudge the owner about the specific gap
🔴 Not readyA gap that can't be fixed in timeDefer to the next window, or escalate
⚪ Out of windowPlanned outside this windowListed for awareness

Design notes

  • Make the criteria data-driven. Each one should map to a tracker field or link. A criterion that can't be checked automatically gets skipped under pressure.
  • Keep thresholds in version-controlled config, not in people's heads.
  • Show the reason, not just the flag. "Not ready: no test evidence" gets fixed faster than a red cell.
  • The evaluation is easy to automate (see the scheduled alerting pattern).

Part 2: The go/no-go meeting (30 min)

Timeline

WhenActivity
T-N daysPull candidates with a saved query; evaluate the gate; publish the readiness report
T-1 dayOwners close gaps; re-run the gate. 🟡/🔴 owners prepare a recommendation (fix, defer or accept the risk)
T-0Meeting. Cancel it if no decision-maker can attend.

Agenda

TimeSegmentOutput
0–5Consent agenda: read out the ✅ items; approve unless someone objectsBulk approval
5–20Exceptions: each 🟡/🔴 owner presents the gap, the options and a recommendationA decision per item
20–25Operational check: on-call, rollback, communicationsConfirmation
25–30Recap: read back each decision and its ownerDecision log entry

Decision options

  • Go: ship as planned
  • Go with conditions: ship if a named condition is met by a set time
  • No-go, defer: move to the next window
  • No-go, escalate: a cross-team blocker needs sponsor input

Decision rule: any failed gate means No-go unless the accountable approver records a waiver that names the risk.

Anti-patterns

  • Walking through every item one by one, whether it's ready or not
  • Deciding without the release owner present
  • Treating "we'll monitor closely" as a mitigation plan
  • Leaving the meeting without written decisions
