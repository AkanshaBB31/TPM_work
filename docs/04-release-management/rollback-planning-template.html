Rollback Planning Template

Skill: Release risk management · Standards: ITIL change enablement, SRE practices

A rollback plan answers one question: if this release goes wrong, how do we get back to a known-good state, and how quickly? Agree it before release day.

1. Summary

FieldValue
Release<version>
Previous known-good version
Rollback decision authoritye.g. on-call engineering lead
Max time to decidee.g. 30 min after the first trigger
Target time to complete rollbacke.g. ≤ 20–30 min
Point of no returnThe step after which only a roll-forward is possible

2. Triggers (any one; values illustrative)

SignalThreshold
Error rate> 2× the pre-release baseline for 10 min
Latency (p95)> 1.5× baseline for 10 min
Critical user journeySynthetic check fails twice in a row
Data integrityAny confirmed corruption
Severity-1 incidentDeclared and attributed to the release

3. Strategy by change type

Change typePreferred rollbackNotes
Feature behind a flagTurn the flag offInstant; no deploy (preferred)
Stateless serviceRedeploy the previous artifact / blue-green switchKeep the previous version warm
Config changeRevert the configVersion-controlled config only
Schema migrationExpand/contract (backward compatible)Avoid destructive migrations in the same release
Data backfillRestore a snapshot / run a compensating jobTake the snapshot before running
Last resortForward fixOnly if the above aren't possible and the fix takes < 1 hour

5. Data considerations

  • Can the old version read data written by the new one?
  • What happens to records created during the release window?
  • Are any migrations irreversible? If so, where's the backup?

6. Rehearsal

  • ☐Rollback rehearsed in pre-production within the last 30 days
  • ☐Measured rollback time: ____ min

7. After a rollback

  • Blameless post-incident review within 3–5 business days
  • Agree the criteria for re-release; run a fresh go/no-go
